# Pitch outline (10-minute talk)

Slide by slide, with speaker time in brackets. The demo can be live (one click on 马上试试 opens a fresh demo bank) with the video as backup.

1. **Title** (0:20). Name: 中联银行 / Central Union Bank, one line: “你说一句，我来办；动钱之前，先问你。/ Say it once. We do it. Money only moves when you say yes.” Team.
2. **The problem** (0:50). Mobile banking hides simple tasks behind deep menus; the brief notes a transfer takes three or more steps. Agents can now act on a customer's behalf, so the hard question is control: who decides that money moves?
3. **Our principle** (0:50). One diagram: words → AI plan (closed catalogue of 43 actions) → code checks it against the customer's own records → 直接办 / 需确认 / 需验证 → the customer's yes → the bank → a reply written by code. The model never sees account data, never approves, never writes a number.
4. **Demo** (4:00). Live, or the 5-minute video cut to 4 ([DEMO.md](DEMO.md)): a sandboxed spending question; “给妈妈转200” on one confirm card; the red transfer to a new seller that is delayed and then returned for a name mismatch; three bypass attempts and the safety lock; the birthday plan, run by moving the bank clock, or stopped and undone in words.
5. **Permission tiers, exactly as the brief** (0:40). Green, yellow and red with the ¥1,000 daily total (counted across requests, scheduled payments and plan steps), signals that only raise, approval bound to a hash of the exact details, PIN plus SMS or passkey. On screen the customer only ever sees plain words: 直接办, 需确认, 需验证, and one reason.
6. **Security in layers** (0:50). Screening → closed plan schema → tiers in code → approval hash → strong verification → delayed arrival and name check → safety lock → hash-chained audit. Make the point that an attack screening misses still lands on a confirm card at the right tier, and that operators can take over a conversation but can never approve for the customer.
7. **Built for banks in China** (0:40). Same-bank and 超级网银 routes; instant, 2-hour or next-day arrival as PBOC notice 261号 requires, with cancellation; name check and returns; RMB in fen; no CDNs; any OpenAI-compatible model, including providers hosted in China; works fully offline with the rule-based planner.
8. **Evidence** (0:40). 160 automated tests; 224 everyday requests and 69 attacks, each on a fresh customer, all passing with the offline planner; no attack ran anything without approval. Say how the sets grew: each time we probed with new phrasings, the misses became fixes and new cases. Say plainly what isn't measured yet (the model planner).
9. **Honest risks** (0:30). Three from [SECURITY.md](SECURITY.md): SMS is a weak factor (prefer passkeys), a coached customer can still approve (mitigated by delays and the name check), and the bank is simulated.
10. **What's next** (0:30). Plug a real payment API into the one transfer module; measure the model planner on the same sets; an IM channel (WeCom or WeChat) that hands red steps back to the app; per-operator two-factor authentication.
11. **Close** (0:10). The one line again, and the ask.

Visual style: the app's own look (green accent, ruled panels, the confirm card, red seals), one idea per slide, Chinese first and English second if the talk is bilingual. Screenshots: the landing phone, a yellow confirm card, a red card with its reason, the transfer stages with both phones, History with “哈希链完整”.
